# Versioning & Release Pipeline

## Version Format

`v<major>.<minor>.<patch>[-suffix]`

Examples: `v4.0.1`, `v4.1.0-alpha`, `v4.2.0-beta`, `v5.0.0-rc1`

The `v` prefix is **required** — the release workflow triggers on the `v*` tag pattern.
Suffix is optional; use `-alpha` / `-beta` / `-rc` for pre-releases.

## Branch → Release Pipeline

```
feat/<name> branch
  → PR opened
      └─ build-linux.yml runs automatically (tests + Linux/Windows builds)
  → PR merged to main
  → git tag vX.Y.Z[-suffix]     ← release trigger
  → git push origin vX.Y.Z[-suffix]
      └─ release.yml runs:
           build-linux  ──┐
           build-windows ─┤ (needs: build-linux)
           create-release ┘ (needs: both) → draft release on GitHub
  → manually review & publish the draft release on GitHub
```

## Tagging a Release

Run these after merging to main:

```bash
git checkout main && git pull
git tag v4.0.1-alpha
git push origin v4.0.1-alpha
```

Then go to **GitHub → Releases** and publish the draft once the workflow completes.

## What CI Produces

**`build-linux.yml`** (PR + push to main):
- Runs frontend tests (Vitest) + Go tests
- Builds Linux binary + Windows binary + NSIS installer (artifacts only, not released)
- PR artifacts auto-expire after 3 days

**`release.yml`** (tag push):
- Builds `KeyLint-vX.Y.Z-linux-amd64` and `KeyLint-vX.Y.Z-windows-amd64.exe`
- Generates `latest.json` for the in-app updater (`UpdaterService.CheckForUpdate`)
- Creates a **draft** GitHub Release with auto-generated notes from PR titles
- All three files are attached to the release

## How AppVersion Is Injected

`main.AppVersion` (in `main.go`) defaults to `"dev"`. Both workflows set it at build time:

```bash
VERSION=$(git describe --tags --always)
go build -ldflags="-X main.AppVersion=${VERSION}" ...
```

`git describe --tags --always` produces:
- `v4.0.1-alpha` — on a clean tag
- `v4.0.1-alpha-3-gabcdef` — 3 commits after the tag (CI only, never release)
- `v4.0.0-5-gabcdef-dirty` — uncommitted changes (build-linux.yml dev builds)

The version is surfaced in Settings → About via `UpdaterService.GetVersion()`.

## What CI Does NOT Do

- No automatic version bump commits
- No `CHANGELOG.md` updates — release notes are auto-generated by GitHub from merged PR titles
- No auto-publish — draft must be manually reviewed and published
- No branch protection enforcement (set that up in GitHub repo settings if needed)

## The bundled WebView2 bootstrapper

The Windows installer bundles `MicrosoftEdgeWebview2Setup.exe`. It is the only
external binary in this pipeline that reaches end users' machines, and until #66
CI downloaded it from a redirector with no check of any kind.

CI now fetches it through `scripts/fetch-webview2.sh`, which refuses to hand over
a file that is not signed by Microsoft.

### What is checked

1. **HTTPS end to end.** `--proto '=https' --proto-redir '=https'`, so a redirect
   onto plaintext is refused rather than followed.
2. **Where the redirector sent us.** The final host must be `microsoft.com` or a
   subdomain. Userinfo is stripped before the port, because
   `https://microsoft.com:443@evil.example.com/x` otherwise parses as
   `microsoft.com` — curl does carry that through to `url_effective`, so it is a
   live bypass and not a hypothetical one. Today the chain ends at
   `msedge.sf.dl.delivery.mp.microsoft.com`.
3. **The Authenticode signature**, which is the gate:

   ```
   osslsigncode verify -index 0 -CAfile build/windows/microsoft-root-ca-2011.pem -in <file>
   ```

`-index 0` matters. These files carry **two** signatures: the primary one from
`CN=Microsoft Corporation` via `Microsoft Code Signing PCA 2024`, and a second,
self-signed `EdgeBuild` certificate that cannot chain anywhere. Without
`-index 0` a perfectly genuine file fails verification because of the second one.

### Why the root is vendored, and how to check it

`Microsoft Root Certificate Authority 2011` is **not** in Ubuntu's
`ca-certificates` bundle, so the system trust store cannot validate this chain.
(The bundle does carry *Microsoft RSA Root CA 2017* and *Microsoft ECC Root CA
2017* — the absence is specific to the 2011 code-signing root, not categorical.
Checking with `grep Microsoft` on that file proves nothing either way: it is
base64 with no subject lines. Compare fingerprints instead.)

So the root lives in `build/windows/microsoft-root-ca-2011.pem`:

| | |
|---|---|
| Source | `https://www.microsoft.com/pki/certs/MicRooCerAut2011_2011_03_22.crt`, the CA Issuers URL in the AIA extension of the intermediate inside the signed file |
| SHA-256 (DER) | `847df6a78497943f27fc72eb93f9a637320a02b561d0a91b09e87a7807ed7c61` |
| Subject | `CN=Microsoft Root Certificate Authority 2011, O=Microsoft Corporation` |

Its provenance does not rest on that URL. The check that matters is
cryptographic: this root **signed the intermediate embedded in the genuine
Microsoft-signed bootstrapper**, which anyone can confirm without trusting
either download —

```
openssl pkcs7 -inform DER -in <extracted-sig>.p7b -print_certs -out chain.pem
openssl verify -CAfile build/windows/microsoft-root-ca-2011.pem -partial_chain <intermediate>.pem
```

Forging that would require Microsoft's private key. Compare the fingerprint
above against any Windows machine's certificate store as a second opinion.

### No digest pin

An earlier version of this pinned a SHA-256 instead. A digest breaks on every
Microsoft update, and each break demands a human judgement about a new binary —
which is exactly the moment someone pastes a hash to turn a red build green. The
signature check answers the question that actually matters ("did Microsoft sign
this?") and keeps answering it when the file changes.

### Local builds are not the release artefact

`build/windows/Taskfile.yml` still calls `wails3 generate webview2bootstrapper`,
which **embeds** a copy rather than downloading one — so local builds keep
working offline and on Windows, where go-task cannot execute a shell script.

Be aware of what that copy is. In `wails/v3@v3.0.0-alpha.72` it was signed in
April 2021 with a certificate that **expired in December 2021**. It is
timestamped, and `osslsigncode` does not validate the countersignature, so it
reads as expired today and the local verification step prints a warning rather
than failing.

That is deliberate, and it is also a real difference: a locally built installer
bundles a four-year-old bootstrapper, while the released one carries whatever
Microsoft serves today. **Ship what CI builds.**

### When the check fails in CI

It means the file Microsoft served is not signed by Microsoft, or the chain
changed. Do not work around it. Reproduce by hand:

```
curl --proto '=https' -fsSL -o /tmp/wv2.exe "https://go.microsoft.com/fwlink/p/?LinkId=2124703"
osslsigncode verify -index 0 -CAfile build/windows/microsoft-root-ca-2011.pem -in /tmp/wv2.exe
```

The realistic innocent cause is Microsoft rotating to a root this repository does
not carry. In that case the new root needs the same provenance argument as the
one above — it must be shown to have signed the intermediate in the file — before
it is added.
